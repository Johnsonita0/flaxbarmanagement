# Flex Bar Web

Responsive React, TypeScript, and Vite application for the Flex Bar staff and business management system.

The UI is grouped by purpose: screen-level views live in `src/pages/`, reusable UI in `src/components/`, and all stylesheets live in `src/css/`. `src/App.tsx` only re-exports the app router.

## Local setup

1. Copy `.env.example` to `.env.local` and set the Supabase publishable key as `VITE_SUPABASE_PUBLISHABLE_KEY` (or use `VITE_SUPABASE_ANON_KEY`) plus the local API URL. The Flex Bar Supabase project URL is already set. Restart Vite after changing environment variables.
2. From this folder, run `npm install`, then `npm run dev`.
3. Run `npm run build` to type-check and build the production frontend.

Only the Supabase publishable/anon key belongs in this browser app. Never put a Supabase service-role key or Cloudflare R2 credentials in `VITE_*` variables.

The frontend is configured as an installable PWA with a manifest and service worker. The branded launch splash appears for 10 seconds on every launch, on mobile, tablet, and desktop. Returning authenticated users see a welcome-back message and are taken to their last visited screen; first-time visitors see the workspace preparation message. User-facing notifications use a shared, dismissible toast system and avoid exposing authentication provider or server details. The Notification inbox tracks updates for the signed-in user; company administrators also receive expandable system-error details and geofence alerts. Selecting a regular notification marks it as read and opens its related module; selecting an alert expands the full message. Browser/device alert permission can be enabled from the inbox. These alerts work while the app is open or its browser session is running; push delivery after the browser is fully closed is not configured. The service worker does not cache API responses or authentication data. The role confirmation screen displays the role assigned to the signed-in profile; it does not let a user grant themselves a different role.

Super admins can register staff accounts with an initial password, manage roles and department assignments from the Staff area, and create departments from Departments. The registration form offers seven starter bar/restaurant assignments. Share initial passwords with staff securely. The super-admin can review attendance but does not have a clock-in action; attendance check-in is for staff and management roles.

Attendance requires a precise GPS reading whose distance plus reported accuracy is within 10 metres of the company's saved location, as well as scanning the rotating on-site QR code. Administrators keep Settings → Business Location / Geofence open on a screen inside the building; staff scan that code from Attendance before clocking in or out. A blocked clock-in that cannot be confirmed within the geofence alerts active company administrators and the staff member's active department head through workspace notifications. Apply the backend migration `20261023_attendance_geofence_qr.sql` before deploying this requirement. GPS and time-limited QR codes can still be spoofed or relayed by a determined user; they are not device-location attestation.

Department heads can start instant department meetings or schedule them for later. Administrators can start or schedule meetings for any department. Instant meetings open the live-call screen immediately and remain joinable for up to eight hours; scheduled rooms open 15 minutes before their start time.

Chat shows colleague profile photos, typing presence, and sent/delivered message receipts. Apply the backend `20261018_chat_receipts_typing.sql` migration for delivery timestamps and participant-authorized private typing presence. Chat supports one-to-one voice and video calls, plus private group calls with up to seven invited colleagues. Participants can add active colleagues to an existing call by searching the company directory; calls are limited to eight people total. Hanging up ends a two-person call for both participants; in a group call, the person who hangs up leaves while the other participants stay connected. A voice call can turn video on during the call; profile photos are shown when participants' cameras are off. Calls can be minimized while their connection, audio, and controls remain active, then restored from the floating call panel. Incoming calls show the caller's name, position, and profile photo when available. Each unanswered invitation expires after one minute and appears in the direct chat with a call-back action. Declining the final unanswered invitation ends the ringing call and closes the caller's screen. Signing out ends an active call and releases its media resources. Stale calls are cleared when the call owner starts another call. Apply the backend `20261018_in_app_calls.sql` migration before using calls; if private call-room connections fail, run the latest idempotent `20261019_repair_in_app_call_policies.sql` in Supabase SQL Editor to recreate both the room authorization function and Realtime policies. Before opening the microphone, the call client checks that the signed-in user is authorized for the room, then joins using a private channel; calls must not be changed to public channels. Check Supabase Realtime settings and the exact connection reason displayed in the call screen when troubleshooting authorization failures. Apply `20261020_single_device_sessions.sql` before deploying single-device sign-in protection: explicitly signing in on a new device replaces the prior session, and the old device is signed out on its next API request or 10-second heartbeat. Restoring an existing session does not take over another active device. Browser microphone and camera permissions are required, and TURN configuration may be needed on restricted networks.

New company owners can register from the standalone `/signup` route. It is intentionally not linked from the existing sign-in screen. Supabase Auth public registration must be enabled with email confirmation, and the company-workspace migration must be applied before enabling it. Registration provisions a company-specific workspace and role-appropriate starter departments.

## Vercel

Push alerts require the backend's `20261021_call_push_subscriptions.sql` migration, backend-only `VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY`, `VAPID_SUBJECT`, and `PUSH_WEBHOOK_SECRET` settings, plus a Supabase Database Webhook on `public.notifications` inserts. Users enable alerts per device from Notifications; once enabled, incoming calls and all workspace notification inserts can alert while the installed PWA is closed. The installer, browser notification, and app icons use the shipped Flex Bar logo.

Create a Vercel project connected to the frontend Git repository and set its Root Directory to `frontend`. Set `VITE_SUPABASE_URL`, either `VITE_SUPABASE_PUBLISHABLE_KEY` or `VITE_SUPABASE_ANON_KEY`, and `VITE_API_BASE_URL` in Vercel project settings. Set `VITE_API_BASE_URL` to the deployed backend's origin, for example `https://your-api-domain.vercel.app`; do not include a port or `/api/v1`, since the frontend adds API paths itself. This value is required for production builds; `localhost:3000` is used only by the local Vite development server. After setting or changing it, redeploy the frontend.

On the backend Vercel project, set `FRONTEND_URL` to the deployed frontend URL and include that exact origin in `FRONTEND_ORIGINS` (for example, `https://your-frontend-domain.vercel.app`). Add any production custom domain origins there too, separated by commas, then redeploy the backend. The frontend and backend must use their actual deployed URLs; local ports are only for local development.
